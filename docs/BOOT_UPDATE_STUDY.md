Author: Huda Mueen. Generated by `bootchain/run_all.py` (run `python3 -m bootchain.run_all` from the repository root). Seed 20261020. Do not edit by hand.

## Labels and model

Verification time = SHA-256 over the image (cycles per byte x bytes / clock) + one signature verification (cycles / clock). Signature cycles are `published` rows of `data/evidence.csv` or `derived from published` times; cycles per byte are `derived from published` throughput. Times are `estimated`. Comparisons with published boot measurements are `modelled` with the error stated beside them. Where a core has no row the Cortex-M4 row is used and marked `proxy`. Sources: `data/raw/S12_boot_sources.md`.

SHA-256 cycles per byte: software median 76.3 (range 75.1 to 109.6, three Cortex-M4 boards); hardware HASH median 2.38 (range 1.91 to 5.15). No vendor reference manual was retrieved; the hardware figure comes from benchmark pages.

Image size: no retrieved source states a PX4 or ArduPilot binary size. The cited limits are 1 MB (early FMUv2 flash) and 2 MB (FMUv3), and the Crazyflie MCU has 1 MB of flash. Image sizes of 0.1 to 2 MB are therefore assumptions bounded by cited limits (`unverified`).

Uncalibrated median absolute error 67 percent over 8 rows (bootstrap 95 percent interval 57 to 84). This is a negative result: the model built from library cycle counts underestimates wolfBoot boot time strongly, because the published hash only row exceeds the modelled hash by about 32 ms (fixed boot work, a slower hash, or both), and because the wolfCrypt implementations and parameter sets differ from the library rows (for example the boot row uses LMS with Winternitz 8 while the cycle row uses w=16, and the ML-DSA rows differ by implementation). On the 3 validation rows the median absolute error is 8 percent (interval 8 to 54, maximum 54). With so few rows and one scale factor across unlike implementations, this validation is weak. Split: `bootchain/results/wolfboot_comparison.csv`.

## 6. Where an immutable root of trust forces replacement

- Boot code in ROM cannot be changed, so its signature algorithm must outlive the device; RFC 9019 recommends post quantum (for example hash based) signatures for such code (`data/raw/S4_migration.md`, RFC 9019 entry).
- Functions built into an integrated circuit cannot change, so a chip must be replaced if its algorithm must change (NIST CSWP 39 section 4.5, in `data/raw/S4_migration.md`).
- A firmware update can add a software post quantum verifier or a parallel post quantum identity chain, but cannot make a ROM rooted classical chain quantum safe (Caliptra example, `data/raw/S4_migration.md`).
- The STM32H563 product page lists ECDSA signature verification and a HASH accelerator; the STM32U5A5 page lists a PKA. Neither page states post quantum support (`unverified`). If the immutable first stage of such a part verifies with a fixed classical block and its key hash is fused, the classification above applies; whether the first stage is replaceable was not checked.
