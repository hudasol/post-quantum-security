## 2. Method

1. Images. `cyclemodel/build_images.sh` builds, outside the repository, the pqm4 speed binaries for PLATFORM=mps2-an386 at commit 5e5cc76d0b072ee7077e58afcbc619a1a67a53b4 (ML-KEM-512/768/1024 clean, m4fspeed, m4fstack with 10 iterations; ML-DSA-44/65/87 clean, m4f, m4fstack with 50 iterations, each iteration a new key pair and message), the repository harness `bench/mcu` (mlkem-native v2.0.0 and mldsa-native v2.0.0 at the pins of `bench/mcu/fetch_libs.sh`, -O2, BENCH_ITERS=10; every call of a target function in the harness run is traced, including its untimed correctness and stack measurement calls, giving 11 to 21 calls per operation), and the external check image.
2. Tracing. `cyclemodel/tracer.py` loads each ELF into Unicorn with the mps2-an386 memory map (peripherals as RAM reading zero, semihosting stops the run), runs from the reset vector, and counts executed instructions by class between entry to and return from each target function (crypto_kem_keypair, crypto_kem_enc, crypto_kem_dec, crypto_sign_keypair, crypto_sign_ctx, crypto_sign_open_ctx and the harness equivalents). Classes: ALU, multiply, multiply accumulate, divide, load, store (LDRD and STRD with an extra word count), LDM/STM with register count, unconditional branch, conditional branch taken and not taken (from the address of the next block), writes to PC, IT, FPU moves, FPU loads and stores, FPU arithmetic, other.
3. Models. Baseline (one cycle per instruction); a priori (per class costs, section 4); fitted (non negative least squares on the training half, each row weighted by the inverse of its published value so that relative error is minimised).
4. Errors. Percent error is (modelled minus published) divided by published. Bootstrap 95 percent intervals over rows.
5. Prediction intervals. With e the held out relative error, the true value is modelled / (1 + e); the 2.5 and 97.5 percentiles of the 27 held out errors give the bounds. With so few held out rows these percentiles are close to the extreme errors.

## 3. Assumptions and limits

* Toolchain differs: images here use arm-none-eabi-gcc (15:13.2.rel1-2) 13.2.1 20231009; the published pqm4 numbers used arm-none-eabi-gcc 11.3.1 20220712 (Arm GNU Toolchain 11.3.Rel1), per pqm4 README (data/raw/S6_pqm4_config.md). Code generation differences enter the error directly; for clean C code this can be large.
* No wait state, cache or bus contention model. The pqm4 benchmark clock modes use zero flash wait states (data/raw/S6_pqm4_config.md); the model therefore describes a zero wait state Cortex-M4 only. The board that produced pqm4 benchmarks.csv is not recorded.
* pqm4 counts cycles with SysTick (core clock, 24 bit with overflow count); the measured window includes call overhead and two timer reads. SysTick overflow interrupts (one per 2^24 cycles) run on the board but not in the emulation.
* Signing is variable time (rejection sampling). The published pqm4 sign value is a mean over its runs; the model uses the mean of 50 traced messages with different keys. Section 5.2 gives the spread.
* The tracer counts IT predicated instructions with a failed condition as executed; it does not model pipelining of neighbouring loads, register dependencies, branch target alignment or the FPU pipeline.
* The a priori costs could not be checked against the Arm Cortex-M4 Technical Reference Manual: the fetch of the instruction timing page was refused on 2026-10-20 and not retried. They are listed as unverified assumptions.
* The fitted costs are not physical cycle costs. With 12 features and few training rows, the non negative fit can trade one class against another; read them as a calibration, not as timing facts.
* Randomness is deterministic (fixed seed generators of each code base); inputs differ from the published runs. A second full run of `cyclemodel/run_all.py` on 2026-10-20 reproduced every instruction count; the ELF hashes in traces.csv changed after a rebuild (the pqm4 build is not byte reproducible), so the hashes identify a build, not the source.
