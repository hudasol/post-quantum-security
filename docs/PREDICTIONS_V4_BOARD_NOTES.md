# Notes on the board predictions (written after the hash, dated)

Author: Huda Mueen. Written 2026-10-20, after `docs/PREDICTIONS_V4_BOARD.md` was hashed and before any board session. The hashed file is not edited; these notes say how it will be scored, in response to an independent review.

1. **In sample rows.** BP22 to BP24 (ML-DSA-44 m4f) and BP28 to BP30 (ML-KEM-768 m4fspeed) predict binaries whose published pqm4 rows were in the training half of the cycle model (`cyclemodel/results/split.csv`). Their published values already lie inside the registered intervals, so a hit there says little. These six rows will be scored and reported separately as a check of the board against published pqm4 numbers, not as a test of the model.
2. **Out of sample rows.** BP1 to BP21 and BP25 to BP27 (24 rows) predict code the model was not fitted on: the repository harness (18 rows, where the model extrapolates beyond the training mix) and pqm4 clean ML-DSA-44 and ML-KEM-768 (6 rows, in the test half). The registered rule (refuted if more than a third of operations miss) will be applied to these 24 rows only. The share of misses, and whether the errors share one sign, will also be reported, because errors on one board are strongly correlated.
3. **Caches.** The model assumes no cache and no wait states. The run protocol records the clock, flash wait states, cache and prefetch state read back from the board; any operation measured with caches or prefetch on will be marked as such beside its verdict, because it does not match the model's conditions.
4. **Point predictions.** The full fit uses per class costs that are not physical cycle costs (for example below one cycle for a plain ALU instruction). For the harness rows the registered interval is the envelope of the full and the reduced fit, which is why those intervals are wide.

## Second note (2026-10-20, after the second review pass, still before any board session)

5. **The pqm4 clean rows are not a clean test either.** BP19 to BP21 and BP25 to BP27 are in the test half, but their intervals were built from the test half errors, which include these same rows, and their published values already lie inside. A board that reproduces pqm4 gives six automatic hits. The primary test of the model is therefore the 18 harness rows alone: the model is refuted if more than a third of them (more than 6) fall outside their intervals, or if more than four fifths of their errors share one sign. The 24 row rule of note 2 is still reported, as a secondary figure.
6. **Mean, not median.** Each prediction is a mean over messages, so each verdict uses the board mean over its runs; the median and the spread are reported beside it. Signing is skewed by rejection sampling, and the board runs more messages than the 11 traced on the host, so the board mean of a signing operation is compared with the prediction and the difference in message count is stated.
7. **Caches decide whether a row counts.** If an operation can only be measured with instruction or data cache or prefetch on, its verdict is reported but does not count toward refutation. The run protocol asks for one pass with caches and prefetch off at zero wait states where the board allows it (`docs/BOARD_RUN_PROTOCOL.md`); if no row can be measured that way, the refutation rule cannot be applied and the session is reported as a check of conditions only.

## Third note (2026-10-20, after the third review pass, still before any board session)

8. **The kit as shipped cannot switch caches off.** `bench/board_kit/` uses the pqm4 clock set up and only reads the cache and prefetch bits back; it has no option to clear them, and this round did not write or test one. A session run with the kit as it stands therefore checks conditions and reproduces published pqm4 rows, but under note 7 it cannot refute the cycle model. A cache off pass needs a change to the start up code, made and tested on the board before the session counts as a test.
9. **The training rows had caches on too.** The pqm4 rows the model was fitted on were measured in pqm4's benchmark mode, which the run protocol records as caches on for both candidate boards. The model's "no cache" condition is therefore an assumption about its own training data as well, so a cache off pass may sit below the predictions for reasons that are not a model error. Both passes, if run, will be reported side by side.
