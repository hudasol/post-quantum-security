# Protocol for round 4

Author: Huda Mueen. Written 2026-10-20 before any work of the round. Predictions: `docs/PREDICTIONS_V4.md` (hashed). Completeness rubric: `docs/COMPLETENESS_RUBRIC.md`.

## Aim

Turn the repository from a sourced review into a complete, independent study: data, validated models, simulations and an answer with an uncertainty to each research question, then a proposal seed for a robotics project. Nothing is measured on a microcontroller in this round; the board experiment is prepared and its outcome predicted.

## Research questions

| ID | Question |
|---|---|
| RQ1 | What do ML-KEM, ML-DSA, SLH-DSA, FN-DSA where published, LMS and XMSS cost in cycles, stack and flash on Cortex-M0+, M4, M7, M33, M55 and MCU class RISC V, and how well can cycles be predicted without a board? |
| RQ2 | What do these operations cost in energy and CPU headroom, and what share of a drone battery or flight controller budget does a realistic security workload take? |
| RQ3 | How do handshake, rekey, signed command and update traffic behave over LoRaWAN, IEEE 802.15.4, MAVLink class telemetry radios, Wi-Fi and NB-IoT or cellular? |
| RQ4 | What do signed boot and signed update cost, and where does an immutable root of trust force hardware replacement? |
| RQ5 | For fleets built from real board classes, which devices can take a firmware update, need a hybrid, or need replacement, and with what probability? |
| RQ6 | Which reference architecture for an authenticated command and update channel is feasible, and what follow on robotics project does the evidence justify? |

## Labels

Published, host measured, emulated, estimated, planned, and two new labels: modelled (trace driven or fitted model, validation error shown beside every value) and RTL simulated (cycle accurate run of an open source core design, never presented as Arm silicon). Board measured stays reserved.

## Work packages, owners and acceptance tests

Each package is run by a separate work stream with a written brief, its input files, its output path and its acceptance test. Verification streams receive no notes, only the source and a blank check sheet.

| Package | Stream | Output | Acceptance test |
|---|---|---|---|
| WP1 literature and data | three extraction streams by topic, then two independent reading streams, then adjudication | `data/raw/S12_*`, `docs/SEARCH_PROTOCOL.md`, `data/bibliography.bib`, `docs/META_ANALYSIS.md` | every new row read by two readers; wrong value rate reported with a Wilson interval; citation check passes |
| WP2 cycle model | one modelling stream | `cyclemodel/`, `docs/CYCLE_MODEL.md` | seeded split recorded; held out errors reported before any modelled value is used |
| WP3 energy and headroom | one modelling stream | `energy/`, `docs/ENERGY_STUDY.md` | every parameter cited or labelled assumption; Sobol indices; tests |
| WP4 links and protocols | one modelling stream | `linksim/`, `docs/LINKSIM_STUDY.md`, `docs/PROTOCOL_SIM.md` | validation table regenerated by one script; closed form checks pass |
| WP5 boot and update | one modelling stream | `bootchain/`, `docs/BOOT_UPDATE_STUDY.md` | comparison with every published boot or update row |
| WP6 fleets and policy | one modelling stream | `data/reference_profiles.csv`, `planner/`, `docs/PLANNER_STUDY.md`, `docs/POLICY_TIMELINE.md` | planner tests and property tests pass; every profile cell sourced or empty |
| WP7 board kit | one build stream | `bench/board_kit/`, `docs/BOARD_RUN_PROTOCOL.md` | images build; emulator log dry run parses fully; board predictions hashed |
