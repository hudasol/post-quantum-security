# Software in the loop study of command authentication over an emulated link

Author: Huda Mueen.

Status: SITL measured (timings that include the flight stack, taken from a flight stack running in software in the loop on the host at a pinned version, with the link emulated) and emulated (quantities produced by the emulated link alone). No timing in this document is a timing on flight hardware, and no radio was used. Generated by `python3 -m sitl.make_doc` from `sitl/results/`.

## 1. Question

Do the availability and the added latency per command that the mission study (`docs/MISSION_STUDY.md`, label estimated) computes for its architectures hold when a real flight stack answers the commands? Four configurations are compared on the same flight stack, the same scripted missions and the same emulated link.

## 2. Set up

- Flight stack: ArduPilot Copter 4.7.2 SITL, built in multicopter model (--model +), speedup 1. PX4 was the first choice; PX4 v1.17.0 (the pinned PX4 checkout of this round) has no MAVLink 2 signing in its MAVLink module (no SETUP_SIGNING handling in src/modules/mavlink), while its later documentation (v1.18) has a page on message signing; to keep one baseline for all four configurations, all four run on ArduPilot, whose documentation describes signing.
- Ground station: pymavlink 2.4.50 in Python 3.13.16; host Intel(R) Xeon(R) Processor @ 2.10GHz, 2 logical cores, Linux 6.18.44-fc-v139.
- Mission: upload (takeoff to 10 m, a 80 m leg north, a 80 m leg east, land), mode AUTO, arm; from arming until the vehicle has landed and disarmed, the ground station sends one COMMAND_LONG (MAV_CMD_DO_SET_SERVO to an output with no function) every 1.0 s, the drone command rate of `mission/traffic.csv`. Latency is the time from the ground send to the COMMAND_ACK of the flight stack arriving back at the ground station.
- Link: a relay between the ground station (UDP) and SERIAL1 of the vehicle (TCP) parses MAVLink frames and sends them over one emulated half duplex channel with the rate, fragmentation and frame loss of the mission study (`linksim/params.csv`, `mission/assumptions.csv`); command, acknowledgement and handshake frames are retransmitted after the timeout of `linksim/params.csv`, telemetry frames are not. tc netem was not used (it needs root and network namespaces).
- Outages: one outage per mission, starting uniformly between 15 s and 40 s after arming, with an exponential duration of mean 5 s (the mission study mean). One outage in a flight of about one minute is close to the 60 per hour point of the mission study outage sweep, which is the study value used for the comparison of availability with outages.
- Seeds: run i of a configuration and profile uses seed 20261021 plus 1000 times the profile index plus 100 times the configuration index plus i; every seed is stored in `sitl/results/missions.csv`.

| configuration | what is on the link | vehicle side delay | mission study architecture used for comparison |
|---|---|---|---|
| 1 no authentication | MAVLink 2 frames as sent | none | unauthenticated stream |
| 2 MAVLink 2 signing as shipped (flight stack) | MAVLink 2 frames with the 13 B signature field added by the flight stack and the ground station (real signing, key provisioned over the wired port with SETUP_SIGNING) | the flight stack itself | D |
| 3 hybrid session with change F1 and per message tag (emulated relay pair) | handshake of 7208 B in four flights (design change F1, the vehicle signs too) before each mission, then 13 B added to every frame by the relay pair; teardown after 10 s without frames and a new handshake | 0.145 ms per command; handshake 42.4 ms | B |
| 4 ML-DSA-44 signature per command (emulated relay pair) | 2420 B added to every command, sent in file transfer style chunks | 8.46 ms per command (ML-DSA-44 verify) | C |

Delays are published cycle counts at the 168 MHz clock of the mission study (`mission/model.py`, data/evidence.csv rows S2-0032 and S2-0033 and the rows of the mission study cycle table); no cryptographic function is executed by the relay pair. The rekey interval of the architecture (300 s) is longer than a mission, so no rekey occurs.

## 5. Reading the comparison

- The mission study defines latency as one way delivery of the command to the vehicle; this study measures the round trip to the flight stack acknowledgement, which adds the acknowledgement air time, the flight stack scheduling and the queue behind telemetry. The one way columns (emulated) are the closer match to the study definition; the round trip columns are the stricter, SITL measured quantity.
- The telemetry load comes from the flight stack: stream rates were set to the drone rates of `mission/traffic.csv` where the integer stream rate parameters allow it, but each stream group carries more messages than the study counts, so the channel is busier than in the study.
- One outage per mission is a forced design, not a Poisson process. Flights last under a minute, so the rate is higher than the 60 per hour sweep point used for comparison, and each configuration draws its own outages (the seed includes the configuration), so the share of flight time in outage differs between configurations. Availability with outages is therefore an order of magnitude check, and differences between configurations of a few hundredths are not resolved.
- The relay of the hybrid configuration enforces no replay rule, so its availability is not that of the recommended design with a sequence rule. The signed commands the flight stack discarded (frames delivered after a newer frame) would also be rejected by the strict next sequence rule of the formal proofs; a deployment needs in order delivery or a replay window that the proofs do not yet cover.
- One way latencies and the handshake time are emulated by the relay from the mission study inputs, so their agreement with the mission study is a consistency check; only the round trips through the flight stack test the model.

## 6. Limits

- Phase locking (fixed by a rerun): a first set of runs sent command k exactly k seconds after arming, so every command of a mission met the periodic telemetry at the same phase and latency differences of tens of milliseconds were not resolved. `sitl/run_missions.py` now draws a random phase for every command from the run seed, and all results in this document come from the rerun with that fix (same seeds). The raw files of the first set are kept in `sitl/raw_run1/` for the record and are not used.
- Acknowledgement matching: the relay of the recorded runs paired acknowledgements with delivered commands in order. With signing the flight stack silently discarded some delivered commands (a frame retransmitted by the emulated link layer arrives after a newer frame and fails the signing timestamp rule), which shifted that order; `sitl/analyse.py` reassigns each acknowledgement to the command delivered at most 0.3 s before it, and the relay now does the same.
- Only the SiK class profile was run; the IEEE 802.15.4 class profile is implemented but has no runs.
- SITL measured timings come from a host with two shared cores; scheduling noise of the host enters every round trip.
- The link is an emulation with independent frame loss, a first in first out shared queue and an assumed radio buffer of 4096 B per direction; it is not a radio.
- Configurations 3 and 4 add bytes and delays only; nothing cryptographic is executed, and the session state machine is the relay pair, not the flight stack.
- ArduPilot accepts unsigned messages on its first serial port (SERIAL0, the wired port of this set up), as its documentation states for USB; the emulated link uses SERIAL1, where signing is enforced.
- 20 missions per configuration and profile give wide intervals for rare events (teardowns).

## 7. Reproduce

```
sh sitl/fetch.sh                      # flight stack at the pinned tag, built outside the repository
sh sitl/run_all.sh                    # all configurations and profiles, about one minute per mission
python3 -m sitl.analyse && python3 -m sitl.make_doc
python3 -m unittest discover -s sitl -t .
```
