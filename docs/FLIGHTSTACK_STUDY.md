## 2. Flash and static RAM

Flash used counts every loaded section at a load address in flash, including the initial values of .data. ArduPilot places a crash log area in the flash the image leaves unused (stated in its `common.ld`); that area is counted as free and listed in the column `flash_crash_log_bytes`. Static RAM counts sections allocated at run addresses in RAM: data plus bss, and sections the linker reserves for stacks. A heap section marks the pool the allocator manages and is not counted. Free static RAM is capacity minus both. It is an upper bound on the RAM that new code can use: the build cannot show the heap that the flight stack fills at start up (task stacks, message buffers, the logger buffer), so the RAM really left is smaller by an amount that only a run on the board can show.

Column `measured`: the boards built here use their measured free flash and free static RAM (the smaller value where both stacks were built); the other boards keep the assumption. ## 5. Limits

1. Static RAM is not run time RAM. The free static RAM is an upper bound; heap use at run time is not visible in a build and is the next measurement to make on a board or in software in the loop.
2. Default configurations only. Vendors and users enable or remove features, which moves flash use.
3. Copter is the only ArduPilot vehicle built; plane and rover images differ in size.
4. Board classes that were not built keep the assumed free share of round 4.
5. The compiler is the distribution package named in `flightstack/pins.csv`, which may differ from the version each project uses for its release binaries, so sizes can differ from the published firmware files; that difference was not measured.

_This tool supports planning. It is not a security guarantee._
